## 2. 按难度分级的 valid rate 对比

### 2.1 口径说明（重要）

两组实验的「请求级别」语义不同，必须分别处理：

- **improved**：每个 (条件, 难度) 显式请求 20 轮 → 分母 = 20，可直接给出「请求该级别时的成功率」。
- **legacy**：难度由 PopulationGame 自主决定，**没有显式请求某个级别**；
  且 invalid 轮次的 `level` 字段为空（教师阶段就失败，未进入级别统计）。
  因此 legacy **无法**给出「请求 L2 时的成功率」——只能给出
  「2400 轮里总计产出 11 个 valid L2 任务 / 114 个 valid L3 任务」。

**结论：两者不能放在同一分母下比较。**正确表述是能力对比（§2.2），而不是速率对比。

### 2.2 能力对比（正确的呈现方式）

| 难度 | legacy：2400 轮内产出的 valid 任务数 | legacy 占总轮次比 | improved：请求时的成功率 |
|------|-----------------------------------|------------------|------------------------|
| L1 | 1006 | 41.92% | 80/80 = 100.0% |
| L2 | 11 | 0.46% | 59/80 = 73.8% |
| L3 | 114 | 4.75% | 67/80 = 83.8% |

> legacy 的 L2/L3 产出占比（0.46% / 4.75%）说明：旧系统在整个 2400 轮预算中
> 几乎**从未真正跑通 L2/L3** —— 它的难度控制器把任务推上去，教师在生成阶段就失败，
> 于是这些轮次连级别标签都没有留下。这正是「伪难度陷阱」的量化表现。

## 6. 真实 API 暴露并修复的一个框架缺陷（重要）

### 6.1 现象

首轮真实 API 运行（240 轮计划）在 A/L2 上只得到 **2/20 = 10%** 的 valid 率，
远低于 L1 的 100%。失败原因高度一致：

```
error_code=1  schema_invalid: 约束 '(a & b) == 0x0F' 中引用了
              未声明的标识符 'x0F'
```

### 6.2 根因

`argus/z3_runner.py::_check_constraint_refs` 用裸正则
`[A-Za-z_][A-Za-z0-9_]*` 切词，把十六进制字面量 `0x0F` 切成 `0` + `x0F`，
于是 `x0F` 被当作「未声明变量」而拒绝整个任务。

L1（LIA/Int）几乎不用十六进制，所以毫发无伤；
**L2 是位向量理论，掩码 `0xFF` / `0x0F` 是标准写法**，于是全线误杀。

这是**框架自身的假阳性**，不是 LLM 的能力问题。

### 6.3 修复（两代）

**第一代**：先替换数字字面量（十六进制/二进制/八进制/十进制/下划线/科学计数）为占位符，
再做标识符扫描；同时补齐 z3 内置白名单（`BitVecVal` / `BV2Int` / `LShR` 等）。

**第二代**：上述替换正则缺少词边界，会连带删掉标识符*内部*的数字——
`x1` → `x`、`BV2Int` → `BV` + `2` + `Int`、`a0` → `a`——
于是白名单里的名字在被查询之前就已被破坏。现已用前后视断言（lookaround）收紧。

回归测试：`tests/test_constraint_generation.py::TestNumericLiteralRegression`（9 例，覆盖两代）。

### 6.4 修复前后对比

| 级别 | 修复前（run 1，49 轮后停止） | 第一代修复后（run 2，中间态） | 两代修复后（run 3，最终） |
|------|---------------------------|---------------------------|----------------------|
| L1 | 20/20 = 100% | 79/80 = 98.8% | 80/80 = 100.0% |
| L2 | **2/20 = 10%** | **57/80 = 71.2%** | **59/80 = 73.8%** |
| L3 | （未跑到） | 47/80 = 58.8% | 67/80 = 83.8% |

> 中间态数值为历史记录（第一代修复后的 run 2）；最终列为当前 `--out_dir` 实测值。
> 修复前数据保留在 `argus-workspace/improved_real_run1_hexbug/` 作为证据，
> 中间态日志保留在 `argus-workspace/improved_real_v1_lexbug/`。
> 两代修复后，护栏拒绝已从失败记录中彻底消失；剩余失败是模型侧 JSON 解析失败
> 与 1 例不支持的变量类型——这是真实的能力边界，不再是框架缺陷。

### 6.5 方法论意义

这一发现本身就是 Task 3 的价值证明：**mock LLM 永远发现不了这个 bug**，
因为 MockLLM 对 L2 返回的是手写的合法 payload。
只有真实模型按自己的习惯写 `0xFF`，才会把这个假阳性暴露出来。

第二代缺陷把这一点推得更尖锐：**测试套件在有残留缺陷时与没有时一样全绿**，
所以「测试通过」并不能为护栏背书。真正暴露它的是逐个重读失败轮次的
`error_reason` 并与原始 `task_json` 对照——靠真实失败记录做归因，而不是靠测试。

## 7. 结论

- L1：real API 下 valid 率 **100.0%**，验收线 80%，**达标**
- L2：real API 下 valid 率 **73.8%**，验收线 30%，**达标**
- L3：real API 下 valid 率 **83.8%**，验收线 15%，**达标**

**能力提升的正确表述**（替代有缺陷的速率对比）：

> 旧系统在 2400 轮预算内只产出 11 个 valid L2 任务和 114 个 valid L3 任务
> （占轮次预算的 0.46% 和 4.75%），实际上从未跑通 L2/L3。
> 四层约束生成框架在被显式要求生成 L2/L3 时，分别达到
> 73.8% 和 83.8% 的成功率，
> 且 L1 保持 100.0% 不退化。
