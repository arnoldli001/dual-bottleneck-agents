# ARGUS全架构最小验证方案：基于DeepSeek V4 Flash、预算10000元以内

## 一、预算分配与成本锚定

### 1.1 总预算分解

**GPU算力（2000元）。** AutoDL RTX 4090 24GB按秒计费，¥2.68/小时起。ARGUS的LLM推理全部走DeepSeek API，GPU仅用于Z3验证的并行调度和沙箱执行。按800轮实验、每轮约10分钟GPU占用计算，总GPU时间约133小时，RTX 4090成本约**357元**。即使加上调试重跑和种群并行开销，预留5倍余量也仅**1800元**。Z3-heavy fixtures的中位验证时间仅5-8毫秒，GPU主要承担任务队列调度和日志I/O，负载很轻。

**API调用（5000元）。** DeepSeek V4 Flash的定价为：输入缓存命中0.02元/百万token，输入缓存未命中1元/百万token，输出2元/百万token。ARGUS全架构每轮实验涉及以下LLM调用：

- 内环任务执行：1次调用，约3000 token
- 免疫修复（触发时）：1-3次调用，每次约2000 token
- 中环圆桌共识：4个Agent × 2轮 = 8次调用，每次约1500 token
- 中环判官校准：3次调用，每次约1000 token
- 中环经验蒸馏：2次调用，每次约2000 token
- 外环元自修改（触发时）：1次调用，约4000 token
- 外环跨域迁移（触发时）：1次调用，约3000 token

每轮平均总token消耗约**30000 token**（输入）+ **8000 token**（输出）。800轮实验的总消耗为**2400万输入token + 640万输出token**。

按DeepSeek V4 Flash定价计算：
- 输入（假设50%缓存命中）：1200万 × 0.02元 + 1200万 × 1元 = **1224元**
- 输出：640万 × 2元 = **1280元**
- 单条件总API成本：约**2500元**

4个条件（A/B/C/D）的总API成本：约**10000元**。

但这是最坏估算。实际上：
- 缓存命中率可以优化到80%以上（通过系统提示词和上下文的稳定前缀），输入成本可降至**500元以内**
- 许多轮次不会触发免疫修复和外环修改，实际调用次数低于估算
- DeepSeek的off-peak价格更低（输出仅$0.6/百万token）

**实际API成本预估：3000-5000元。**

**存储与网络（500元）。** AutoDL数据盘（100GB）约200元/月，实验周期1个月。向量数据库和日志存储使用本地文件系统（SQLite + FAISS），无需额外云服务。

**总计：5300-7300元，在1万元预算内。**


## 二、全架构实现方案：基于DeepSeek API的完整ARGUS

### 2.1 关键设计决策：LLM API替代本地模型

ARGUS的L0基座层不部署本地LLM。所有LLM调用（任务执行、免疫修复、圆桌共识、经验蒸馏、元自修改）通过DeepSeek V4 Flash API完成。这带来三个优势：

**第一，消除了GPU内存约束。** 24GB显存的RTX 4090无法部署70B级别模型。通过API调用，ARGUS可以使用284B MoE的DeepSeek V4 Flash，其推理能力远超本地可部署的任何模型。

**第二，成本可控。** DeepSeek V4 Flash的缓存命中输入价格仅0.02元/百万token，意味着系统提示词、宪法规则、经验原则库等稳定上下文可以被缓存，每轮实验的增量token消耗极低。

**第三，并发能力。** DeepSeek API支持并发请求，ARGUS的种群博弈（多个Agent并行出题/解题）和圆桌共识（多Agent并行发言）可以真正并行执行，而非串行等待。

### 2.2 性能优化：缓存策略与批量调用

**系统提示词缓存。** ARGUS的每个Agent角色（教师、学生、验证者、判官）有固定的系统提示词。通过将所有系统提示词放在API调用的最前缀，DeepSeek的自动缓存机制会命中这些稳定前缀，将输入成本从1元/百万token降至0.02元/百万token。缓存命中率预计可达**85%以上**。

**批量调用合并。** 圆桌共识的4个Agent发言可以合并为单次API调用（在prompt中模拟4个角色的多轮对话），而非4次独立调用。这减少了网络往返开销和token消耗。

**上下文压缩。** 每轮实验的上下文（历史经验、当前任务、宪法规则）通过语义压缩后注入，而非全量注入。目标是将每轮输入控制在5000 token以内。

**分级模型路由。** 简单任务（如格式检查、日志摘要）使用DeepSeek V4 Flash的轻量调用；复杂任务（如元自修改、跨域迁移）使用同一模型的完整推理模式。DeepSeek API支持在同一模型上通过system prompt区分推理深度。

### 2.3 健壮性设计：避免重试和报错

**设计原则：失败不是异常，失败是正常状态。**

ARGUS的进化机制天然需要处理失败——免疫修复、凋亡、经验蒸馏都建立在失败案例之上。因此，系统不应将API失败视为需要“重试”的异常，而应将其视为可以“吸收”为经验的事件。

**HTTP 429处理。** DeepSeek API在并发超限时返回429错误码。处理策略不是简单重试，而是：

- **指数退避 + 抖动**：在1秒、2秒、4秒、8秒的间隔后重试，配合随机抖动防止重试风暴
- **最大重试次数3次**：超过3次则将当前任务标记为“API受限失败”，写入经验记忆，切换到下一个任务
- **熔断器模式**：当连续5次API调用失败时，熔断器打开，暂停所有API调用30秒，然后进入半开状态测试

**幂等性保障。** 每个任务有唯一ID。API调用附带`idempotency_key`，如果响应超时但实际成功，重试时服务端会返回缓存的响应而非重复执行。

**超时分级。** 简单任务（如经验检索）超时10秒；复杂任务（如元自修改）超时120秒。超时后不重试，而是记录为“超时失败”，触发免疫修复流程。

**Fallback链。** 如果DeepSeek API连续失败，自动切换到MiniMax M3作为备用（输入2.1元/百万token，输出8.4元/百万token）。Fallback链配置在L5治理层，由Agent自主管理。

**本地缓存兜底。** 每个API调用的输入-输出对存储在本地SQLite中。如果相同或高度相似的输入再次出现，直接返回缓存结果，不调用API。这同时降低了成本和延迟。

### 2.4 全架构功能保留与实现映射

ARGUS的22条设计思路全部保留，但部分机制以简化版本实现：

| ARGUS机制 | 全架构设计 | 最小验证实现 | 简化说明 |
|-----------|-----------|-------------|----------|
| **L1经验记忆** | 向量数据库+图数据库 | SQLite + FAISS本地索引 | 使用FAISS的Flat索引，支持百万级向量检索 |
| **L1甲基化标记** | 稀疏掩码层 | JSON字典存储上下文-行为关联 | 模拟甲基化机制，不涉及真实模型权重 |
| **L1抗体库** | 语义检索修复模式 | SQLite全文检索+关键词匹配 | 使用FTS5全文检索，避免向量服务依赖 |
| **L2免疫修复** | 树突状细胞算法 | 规则引擎+LLM辅助修复 | 危险信号检测用规则，修复方案生成用LLM |
| **L2凋亡/自噬** | 种子花园机制 | 经验压缩+规则合并 | 将凋亡Agent的Top规则合并到主Agent |
| **L2工具合成** | 运行时工具创建 | 预定义工具池+参数变异 | 不实现真正的代码生成，工具参数由LLM变异 |
| **L3形式锚定** | Lean/Z3/沙箱 | **Z3完整实现** | Z3是核心验证锚点，完整保留 |
| **L3圆桌共识** | CVP协议 | 4角色盲评+置信度加权 | 完整实现CVP的评分和收敛检测 |
| **L3判官校准** | WMV + Jury-on-Demand | 简单加权投票 | 判官权重根据历史准确率动态调整 |
| **L4 HAP种群博弈** | 教师-学生极小极大 | 3 Agent种群（教师/学生/验证者） | 种群规模缩小但博弈机制完整 |
| **L4元自修改** | HyperAgents双模式 | 提示词+技能库变异 | 不修改模型权重，只修改可编辑工件 |
| **L4跨域迁移** | 类比引导 | 规则跨任务类型迁移 | 将A任务类型的成功规则映射到B类型 |
| **L5分层宪法** | 核心+适应性规则 | JSON配置+硬编码检查 | 核心规则不可修改，适应性规则可进化 |
| **L5检查点/回滚** | git tag | 本地文件快照 | 每轮实验后保存完整状态快照 |

**关键：Z3形式锚定完整实现。** Z3是ARGUS的“防自嗨阀”。每个Agent生成的Z3编码必须通过Z3求解器验证。验证结果（SAT/UNSAT/timeout/error）作为唯一的真值信号。圆桌共识和LLM判官只用于生成任务和评估任务难度，不用于确定答案是否正确。

### 2.5 Z3任务设计

**任务类型。** 三类难度：
- Level 1：线性整数算术（LIA），10个变量以内
- Level 2：位向量（BV），20个变量以内
- Level 3：混合理论（LIA + BV + 数组），30个变量以内

**任务生成。** 教师Agent生成Z3约束集，学生Agent尝试求解。教师的任务生成正确性由Z3验证器检查——如果生成的约束集本身是UNSAT（矛盾），则该任务无效，不进入种群。

**真值锚定。** 每个任务的正确答案由Z3求解器给出（SAT/UNSAT）。LLM的答案必须与Z3结果一致才算正确。这彻底消除了自确认循环——LLM无法“说服”Z3改变答案。

**难度自适应。** 教师Agent根据学生Agent的实时成功率调整任务难度。如果学生成功率>80%，教师提升难度；如果<30%，教师降低难度。这是HAP博弈的简化实现。

### 2.6 四条件实验设计

| 条件 | 形式锚定 | 种群博弈 | 经验蒸馏 | 圆桌共识 | 预期行为 |
|------|---------|---------|---------|---------|----------|
| A | 无（LLM自评） | 无 | 无 | 无 | 自确认循环，Δ_t持续扩大 |
| B | Z3 | 无 | 无 | 无 | 有锚定但无难度自适应 |
| C | 无（LLM自评） | 有（3 Agent） | 无 | 无 | 有难度自适应但信号不可靠 |
| D（ARGUS） | Z3 | 有（3 Agent） | 有 | 有 | 锚定+种群+蒸馏+共识协同 |

条件A的LLM自评机制：Agent生成Z3编码后，LLM自己判断编码是否正确。条件C的种群博弈：3个Agent互相出题、互相评估，但评估信号来自LLM自评而非Z3。

### 2.7 日志与复现设计

**每轮记录内容：**
- 任务ID、难度级别、Z3约束集原文
- Agent生成的编码、LLM自评分、Z3验证结果
- 求解耗时（毫秒）、token消耗
- 圆桌共识得分、判官权重
- 是否被保留（keep/discard）、git commit hash

**日志格式。** TSV（制表符分隔），每行一个任务，与Karpathy的autoresearch模式一致。日志文件自动生成，不手动输入。

**复现指南。** GitHub仓库包含：`config.yaml`（实验配置）、`agent.py`（Agent代码）、`spec.md`（任务规范）、`requirements.txt`（依赖版本）、`run.sh`（一键运行脚本）、`logs/`（完整实验日志）。


## 三、测试与结果论证

### 3.1 核心指标

| 指标 | 定义 | 数据来源 |
|------|------|----------|
| **编码正确率** | Z3验证通过的任务比例 | Z3求解器输出 |
| **自评-真实差距（Δ_t）** | LLM自评分与Z3验证结果的逐轮差距 | 逐轮记录 |
| **难度扩展率** | Level 3任务占比随轮次的变化 | 任务日志 |
| **圆桌共识可靠性** | 共识结果与Z3一致的比例 | 交叉验证 |
| **Token效率** | 每提升1%正确率消耗的token数 | API调用日志 |
| **进化停滞点** | 正确率不再提升的轮次 | 学习曲线 |

### 3.2 预期核心发现

**发现一：条件A的Δ_t持续扩大。** 这与“Verification Collapse”论文的发现一致——纯自评分组的验证差距在迭代中持续扩大。条件A的Δ_t曲线将从初始的0.2-0.3扩大到0.5以上。

**发现二：条件C的Δ_t先降后升。** 种群博弈在初期改善了难度自适应，但缺乏形式锚定导致种群后期产生“伪难题”——LLM认为困难但Z3可以轻松求解的约束集。Δ_t在第50轮后开始回升。

**发现三：条件D的Δ_t稳定在低水平。** Z3形式锚定持续过滤伪难题，种群博弈维持难度自适应。Δ_t稳定在0.1以下，难度从Level 1逐步扩展到Level 3。

**发现四：条件D的token效率最高。** 条件A由于自确认循环需要大量重复调用；条件C由于伪难题导致无效探索；条件D的每token正确率提升最高。

### 3.3 消融实验

**消融一：移除圆桌共识。** 对比条件D与“D-共识”（Z3+种群+蒸馏但无共识）。预期共识对最终正确率的影响较小，但对Token效率影响较大（共识减少了无效探索）。

**消融二：移除经验蒸馏。** 对比条件D与“D-蒸馏”。预期蒸馏对早期轮次影响不大，但对后期（>100轮）的正确率维持有显著影响。

**消融三：种群规模。** 对比3 Agent vs 5 Agent vs 单Agent。预期5 Agent在难度扩展率上优于3 Agent，但token消耗增加。

### 3.4 统计方法

- 配对t检验或Wilcoxon符号秩检验，比较条件D与A/B/C的最终正确率
- Benjamini-Hochberg FDR校正控制多重比较
- 报告Cohen‘s d效应量和置信区间
- 每个条件运行3次独立实验（不同随机种子），报告均值和标准差


## 四、工程落地：从零到实验的步骤

### 4.1 环境搭建（1天）

**AutoDL实例配置。** 选择RTX 4090 24GB，镜像选择PyTorch 2.x + CUDA 12.x。安装依赖：`pip install z3-solver openai faiss-cpu sqlite-utils`。

**DeepSeek API密钥。** 在DeepSeek平台注册账号，获取API密钥。API Base URL：`https://api.deepseek.com/v1`。模型名称：`deepseek-v4-flash`。

**验证环境。** 运行以下代码确认Z3和API可用：

```python
from z3 import *
x = Int('x')
solve(x > 5, x < 10)  # 应输出 [x = 6]

from openai import OpenAI
client = OpenAI(api_key="your-key", base_url="https://api.deepseek.com/v1")
response = client.chat.completions.create(
    model="deepseek-v4-flash",
    messages=[{"role": "user", "content": "Hello"}]
)
print(response.choices[0].message.content)
```

### 4.2 Agent实现（3天）

**核心Agent类。** 实现一个`ARGUSAgent`类，包含：
- `execute_task(task)`: 生成Z3编码
- `immune_repair(task, error)`: 失败时调用LLM修复
- `generate_task(difficulty)`: 教师Agent生成任务
- `evaluate(task, solution)`: Z3验证

**圆桌共识模块。** 实现4个角色的盲评和置信度加权。每个角色有独立的system prompt，通过单次API调用模拟多轮讨论。

**经验蒸馏模块。** 从成功/失败轨迹中提取规则。使用DeepSeek API进行对比蒸馏，输出正规则和负规则。

**健壮性封装。** 实现`SafeAPIClient`类，封装指数退避、熔断器、幂等性和本地缓存。

### 4.3 实验运行（5-7天）

**条件A/B/C/D并行运行。** 每个条件使用独立的AutoDL实例（或同一实例的多进程）。每轮实验约10分钟，200轮约33小时。4个条件并行运行，总时间约33小时（考虑调试和失败重跑，预留3天）。

**日志监控。** 每轮结束后自动保存TSV日志。使用`tail -f logs/condition_D.tsv`实时监控。

**异常处理。** 如果实验中断，从最近的检查点恢复。检查点包含完整状态快照（经验库、抗体库、宪法规则、甲基化标记）。

## 五、性能优化与健壮性清单

**API层：**
- 系统提示词前缀稳定化 → 缓存命中率>85%
- 指数退避 + 抖动 → 429错误后自动恢复
- 熔断器 → 连续失败后暂停，防止雪崩
- 本地SQLite缓存 → 相似输入直接返回，不调用API
- Fallback到MiniMax M3 → DeepSeek不可用时自动切换

**Z3层：**
- 求解超时10秒 → 超时任务标记为“求解失败”，不重试
- 编码语法检查前置 → 无效编码直接拒绝，不调用Z3
- 并行求解 → 多个任务同时验证，GPU调度

**存储层：**
- SQLite WAL模式 → 并发读写不阻塞
- FAISS Flat索引 → 百万级向量检索<100ms
- 每轮检查点 → 中断后可恢复

**监控层：**
- 每轮记录token消耗 → 实时监控预算
- API错误率监控 → 超过10%触发告警
