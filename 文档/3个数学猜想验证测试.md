## 三个用有限算力验证的未解数学问题
基于搜索结果中已发表的AI数学发现案例，以下三个开放问题最适合用ARGUS架构进行有限算力验证。筛选标准：计算可枚举、验证确定性高、已有AI或人类计算搜索的进展记录、单次验证成本在可控范围内。
### 候选一：Erdős问题中的“Type 1”子集（推荐优先级最高）

**问题性质。** 一项2026年的系统研究将353个Erdős问题分类：310个被归类为“Type 1”——这些问题在识别出单一的结构性事实（sub-lemma）后即可解决，该结构性事实通常可以用Lean 4中的基础证明策略（norm_num、ring、field_simp、omega、linarith）在两行内完成证明。所有结果已在Lean 4中机器验证，零sorry。

**为什么最适合ARGUS验证。** 首先，验证是确定性的——Lean 4内核以“通过或不通过”的方式判定证明是否可编译，不存在自验证悬崖问题。其次，已有成功先例：DeepMind的AlphaProof Nexus用进化搜索解决了9个Erdős开放问题，每个问题成本约200-400美元，且这9个问题全部落在Type 1类别内。这意味着ARGUS的种群博弈机制可以直接对标这一基准。第三，Formal Conjectures基准提供了2615个Lean 4形式化的问题声明，其中1029个是开放的，为ARGUS提供了现成的验证目标库。

**验证方法。** ARGUS的教师Agent从Erdős问题库中筛选Type 1问题，学生Agent尝试构造sub-lemma并用Lean 4证明。Z3锚定层被替换为Lean 4验证器——只要证明编译通过，结果就是确定的。核心指标是：ARGUS在相同算力预算下，能否复现AlphaProof Nexus的9/353解决率，或能否在Formal Conjectures的开放问题上取得首个内核验证的证明。

**所需算力。** 主要是Lean 4编译开销（CPU密集型），LLM调用用于生成证明策略。单问题的证明搜索可能只需要数十次API调用。总计预计不超过100元API费用和数十GPU小时。


### 候选二：Brocard-Ramanujan方程的计算扩展

**问题性质。** 方程 \(n! + 1 = m^2\) 是数论中最古老的开放问题之一。目前已知解仅为Brown数对 \((n, m) = (4, 5), (5, 11), (7, 71)\)。最强无条件结果是否定 \(7 < n < 10^{15}\) 范围内存在解。

**为什么适合ARGUS验证。** 该问题有一个极其高效的验证机制：二次剩余筛法。该方法通过寻找一个素数 \(p\) 使得 \(\left(\frac{n! + 1}{p}\right) = -1\) 来快速排除候选 \(n\)，在标准等分布启发式下，期望两次Legendre符号求值即可排除一个非解，实现近线性总复杂度。搜索已推进到 \(n < 10^{15}\)，测量到的加速比超过440倍。验证一个候选解是否成立，只需要精确整数算术检查 \(n! + 1\) 是否为完全平方数——这是确定性的，没有模糊空间。

**验证方法。** ARGUS的种群博弈可以用于优化筛法的参数选择（素数选择策略、模数配置），教师Agent提出筛法变体，学生Agent在给定搜索区间上运行并报告结果，Z3锚定层验证所有“已排除”声明的正确性。核心指标是：ARGUS能否在现有搜索边界（\(10^{15}\)）之外扩展一个可验证的区间，或能否发现现有筛法中的参数优化。

**所需算力。** 这是三个候选中算力需求最低的。筛法本身是CPU密集但极度轻量的。在AutoDL的CPU实例上运行数千小时的成本约200-400元。LLM调用仅用于筛法参数优化，量级很小。


### 候选三：Collatz猜想在 \(2^{71}\) 边界的扩展验证

**问题性质。** Collatz猜想（所有正整数最终都到达1）已被计算验证到 \(2^{71}\)。2025年的工作将验证极限从 \(2^{68}\) 推进到 \(2^{71}\)，使用分布式GPU计算。2026年的进一步工作将验证范围扩展到 \([2^{71}, 2^{71} + 2^{40})\)，确认该区间内所有整数都下降 below其起始值，从而将验证覆盖扩展到 \(2^{71} + 2^{40}\)。

**为什么适合ARGUS验证。** 验证是完全确定性的——对每个 \(n\)，只需迭代Collatz映射直到值降到 \(n\) 以下。这是一个纯粹的计算任务，没有证明搜索的不确定性。ARGUS的价值在于优化验证算法的效率：搜索结果表明，不同的筛法配置和GPU加速策略对验证吞吐量有显著影响（Barina的方法在128位下每秒可验证更多整数）。ARGUS的种群博弈可以用于搜索最优的筛法参数组合，元自修改机制可以用于优化验证器的代码。

**验证方法。** 教师Agent生成不同的筛法配置（残留类筛选阈值、模数选择、GPU内存布局），学生Agent在给定区间上运行验证并报告吞吐量，Z3锚定层验证所有“已下降”声明的正确性（只需检查每个 \(n\) 的轨迹是否确实在某一步降到了 \(n\) 以下）。核心指标是：ARGUS能否在相同硬件预算下，将验证吞吐量提升到超过Barina的基线。

**所需算力。** 这是三个候选中GPU需求最高的，但仍然是可控的。验证 \(2^{40}\) 个整数需要大量的GPU时间，但ARGUS不需要覆盖全部区间——只需要在一个足够大的子区间上证明吞吐量优势。预计需要约500-1000 GPU小时的RTX 4090，成本约1300-2700元。


### 优先级建议与验证策略

**第一优先级：Erdős Type 1问题。** 验证门槛最低（Lean 4内核判定），已有AI成功先例作为直接对照基准，且Formal Conjectures提供了现成的开放问题库。如果ARGUS能在这个基准上取得任何内核验证的新证明，就是自进化能力有效性的直接证据。预期总成本不超过300元。

**第二优先级：Brocard-Ramanujan筛法优化。** 计算成本极低，验证确定性高，且筛法参数优化是一个定义清晰的搜索空间。即使没有发现新的数学结果，证明ARGUS在筛法效率上超越人类手工调参也是一个有价值的工程贡献。预期总成本不超过500元。

**第三优先级：Collatz边界扩展。** 计算成本相对较高，但验证的确定性最强，且结果的可复现性最好（任何人都可以独立运行验证器检查相同的区间）。建议作为“算力充足时的扩展实验”，而非主实验。

**联合策略。** 建议将Erdős问题和Brocard-Ramanujan作为并行验证目标——前者验证ARGUS的证明搜索能力，后者验证其数值优化能力。Collatz作为压力测试，仅在主要实验完成后根据剩余预算决定是否运行。这种组合覆盖了ARGUS的两个核心机制（形式锚定证明搜索 + 种群博弈数值优化），且总成本在1000元以内，远低于1万元预算。



# ARGUS架构的能力边界与简化重构

## 一、先做减法：现有ARGUS架构与五原则的冲突诊断

在回答“能实现哪些功能”之前，必须先诚实地诊断现有ARGUS架构与用户提出的五原则之间的冲突。否则，任何功能列表都建立在不可落地的地基上。

**与原则1（保持简单）的冲突。** ARGUS设计了五层三环、14个自定义插件、22条机制。dsh在开发这套系统时，需要同时理解`argus-methylation`、`argus-apoptosis`、`argus-antibody`、`argus-roundtable`等一堆私有抽象。这些工具在模型的训练数据中几乎不存在，dsh需要从零学习每个插件的接口语义。更严重的是，14个插件意味着dsh在每一步决策时要在14个工具间做选择——这正是“工具越多，模型越纠结”的典型场景。

**与原则4（写操作单线程）的冲突。** ARGUS的种群博弈设计让3个Agent并行出题、解题、评估。如果它们同时写入`experiences.db`或`methylation.json`，就会产生写冲突。SQLite的WAL模式能缓解并发读，但不能解决并发写。

**与原则2（保持透明）的冲突。** 甲基化标记的“激活-衰减”过程、凋亡的“种子提取”、免疫修复的“抗体检索”——这些机制都在黑箱中运行，用户看不到“为什么这个Agent被判定为凋亡”或“为什么这条经验被激活”。透明性被牺牲在了架构的复杂性里。

**与原则5（成本算清楚）的冲突。** 圆桌共识的4角色盲评、免疫修复的多轮重试、外环元修改的探索——这些机制的成本在架构阶段是模糊的。多Agent不是免费的，它用更多的底层资源换取处理能力，必须评估任务价值是否值得。

**结论：现有ARGUS架构需要大幅简化。** 保留其核心洞察（形式锚定、种群博弈、经验沉淀），但用最少的工具和最简单的结构实现。以下重新设计一套符合五原则的架构。


## 二、简化架构：S-ARGUS（Simple ARGUS）

### 2.1 核心设计决策

**用bash替代自定义插件。** dsh的训练数据中有海量bash命令。`python solve.py`、`cat task.json`、`git diff`——这些表达在训练数据中出现频率极高。而`argus-methylation.activate(context_hash)`这种私有接口，dsh需要从零学习。因此，S-ARGUS的所有操作都通过bash命令和标准文件操作完成，不使用任何dsh插件。

**用文件系统替代数据库。** 经验存储不需要SQLite+FAISS。一个目录`experiences/`，每个经验一个JSON文件，文件名包含时间戳和类型。检索用`grep`和`ls -t`。百万级向量检索在最小验证中根本用不到——200轮实验最多产生几千条经验。

**用单线程执行替代并行种群。** 种群博弈的“多Agent”可以用单线程的顺序模拟实现：教师生成任务→写入文件→学生解题→写入文件→验证器验证→写入文件。三个角色顺序执行，共享同一个工作目录。这完全避免了写冲突，代价只是失去了真正的并行加速——但在200轮、每轮秒级的实验规模下，顺序执行完全可接受。

**用确定性验证器替代圆桌共识。** 圆桌共识的4角色盲评本质上是“用多个LLM的判断来逼近真值”。但如果任务本身有确定性验证器（Z3、Lean、Python测试），圆桌共识就是多余的。S-ARGUS只在确定性验证器不可用时才回退到LLM判断，且只用一个判官，不用4个。

### 2.2 S-ARGUS架构总图

```
┌─────────────────────────────────────────────────────────┐
│                    S-ARGUS 工作目录                       │
│                                                         │
│  tasks/              ← 任务池（教师生成，只增不改）        │
│    task_001.json                                        │
│    task_002.json                                        │
│                                                         │
│  solutions/          ← 学生解答（每轮覆盖）               │
│    task_001_sol.py                                      │
│                                                         │
│  experiences/        ← 经验库（只增不改，grep检索）        │
│    20261012_143022_positive.json                        │
│    20261012_143055_negative.json                        │
│                                                         │
│  harness/            ← 可进化工件（外环修改目标）          │
│    system_prompt.txt                                    │
│    skill_library.md                                     │
│                                                         │
│  logs/               ← 完整对话记录（透明性保障）          │
│    round_001.jsonl                                      │
│    round_002.jsonl                                      │
│                                                         │
│  constitution.json   ← 不可修改的核心规则                 │
│  checkpoint/         ← 检查点（每轮快照）                 │
└─────────────────────────────────────────────────────────┘
```

**核心执行循环（单线程）：**

```
for round in 1..200:
    # 1. 教师：生成任务
    bash: python teacher.py --level {current_level} --output tasks/task_{round}.json
    
    # 2. 验证任务有效性（Z3确定性验证）
    bash: python verify_task.py tasks/task_{round}.json
    
    # 3. 学生：解题
    bash: python solver.py tasks/task_{round}.json --output solutions/task_{round}_sol.py
    
    # 4. 确定性验证（Z3执行）
    bash: python verify_solution.py solutions/task_{round}_sol.py
    
    # 5. 记录日志（透明性保障）
    bash: python log_round.py --round {round}
    
    # 6. 经验沉淀（如果成功或失败有教训）
    bash: python distill.py --round {round}
    
    # 7. 每20轮检查是否触发外环
    if round % 20 == 0:
        bash: python meta_check.py  # 检测停滞
```

**每一步的输入输出都是文件，每一步的结果都可被用户直接查看。** 用户可以用`cat logs/round_045.jsonl`看到第45轮的完整对话，用`grep "positive" experiences/*.json`找到所有正面经验。

### 2.3 工具清单（精简到6个）

| 工具 | 替代的ARGUS插件 | dsh训练数据中的常见表达 |

| `bash` | 所有插件的执行层 | 核心工具，训练数据中无处不在 |
| `read_file` | `argus-exp-store`检索 | `cat`、`head`、`tail` |
| `write_file` | `argus-exp-store`写入 | `echo >`、`tee` |
| `edit_file` | `argus-mutation` | `sed`、`patch` |
| `grep_search` | `argus-antibody`检索 | `grep`、`rg` |
| `run_python` | `argus-sandbox` | `python`、`pytest` |

**6个工具，全部是dsh训练数据中的高频表达。** 没有私有抽象，没有需要学习的插件接口。


## 三、S-ARGUS能实现的功能

### 3.1 核心功能（已验证可行）

**功能一：自主任务生成与难度自适应。** 教师Agent读取当前难度级别，生成对应难度的Z3约束集，写入`tasks/`。验证器检查任务有效性（约束集不能自相矛盾）。学生解题后，根据成功率调整难度级别（>80%升级，<30%降级）。这是HAP种群博弈的简化实现，去掉了“种群”但保留了“难度自适应”的核心机制。

**功能二：确定性验证锚定。** 每个任务和每个解答都通过Z3验证器检查。任务的SAT/UNSAT由Z3确定，学生的答案必须与Z3一致才算正确。这彻底消除了自确认循环——LLM无法“说服”Z3改变答案。这是ARGUS形式锚定层的最简实现。

**功能三：经验原则化沉淀。** 每轮结束后，从成功和失败的轨迹中提取抽象原则（“对于含数组的约束，先展开数组再求解效率更高”），存入`experiences/`。经验以JSON文件存储，用`grep`检索。不做FAISS向量检索——在几千条经验的规模下，`grep`的关键词匹配已经足够。

**功能四：外环元自修改。** 每20轮检测一次性能停滞。如果连续20轮正确率无提升，触发元修改：LLM读取当前`harness/system_prompt.txt`和`harness/skill_library.md`，生成改进版本，通过宪法检查后写入。旧版本保存在`checkpoint/`中，可回滚。

**功能五：完整透明性。** 每轮的完整对话（教师生成任务的prompt、学生的解题prompt、验证器的输出）以JSONL格式写入`logs/`。用户可以用`jq`、`grep`、`less`直接查看每一步的真实环境结果。所有文件变更通过`git`追踪，每个检查点有git tag。

**功能六：成本实时监控。** 每轮记录token消耗到`logs/`。累计消耗超过预算阈值时，自动停止实验并发出告警。

### 3.2 可选功能（根据任务价值决定是否启用）

**功能七：跨任务类型迁移。** 当Z3任务从“线性算术”扩展到“位向量”时，将线性算术的成功经验通过`grep`检索出来，注入位向量任务的prompt。这是跨域迁移的最简实现——不做“类比引导”，只做“关键词匹配的经验复用”。

**功能八：多模型Fallback。** DeepSeek V4 Flash连续失败5次后，切换到MiniMax M3。切换逻辑写在`bash`脚本中，不引入新工具。

**功能九：任务池扩展。** 当教师生成的任务被验证为“过于简单”（学生成功率>95%）时，自动标记为“已掌握”并从任务池中移除。任务池的多样性由教师Agent的prompt控制。

### 3.3 明确不实现的功能（以及为什么不实现）

| ARGUS原设计 | 不实现的原因 | 替代方案 |
|------------|-------------|----------|
| 甲基化标记 | 增加复杂度，收益不明确 | 用`experiences/`中的上下文标签替代 |
| 抗体库（FTS5） | SQLite FTS5的检索质量与`grep`在千级规模下无显著差异 | 用`grep -r`检索`experiences/` |
| 圆桌共识（4角色） | 确定性验证器已提供真值，圆桌共识多余 | 确定性验证器 + 单一LLM判官（仅回退时） |
| 凋亡/种子花园 | 200轮实验不涉及Agent死亡场景 | 简化为“经验压缩”：每50轮将低置信度经验合并 |
| 三层锚定（硬/软/共识） | 最小验证只用Z3硬锚定 | 硬锚定 + 单一LLM判官回退 |
| 可进化宪法 | 12条核心规则不需要在200轮内进化 | 固定宪法，人工审查 |
| 梦境巩固 | 需要跨会话的离线处理，工程复杂 | 不做 |
| 表观遗传跨代传递 | 需要多代Agent，200轮实验不涉及 | 不做 |


## 四、五原则的逐条落地

### 4.1 保持简单

**落地方式：** 6个工具，1个工作目录，3个角色（教师/学生/验证器），全部通过bash和文件操作完成。dsh不需要学习任何私有插件。所有命令都是`python xxx.py --arg value`的标准形式。

**验证方法：** dsh在开发S-ARGUS时，第一次运行不需要阅读任何接口文档，仅从`README.md`和`--help`输出就能理解每个脚本的用法。

### 4.2 保持透明

**落地方式：**
- 每轮的完整对话写入`logs/round_NNN.jsonl`，包含输入prompt、输出、Z3验证结果、耗时
- 所有文件变更通过`git diff`可查
- 每20轮的检查点保存在`checkpoint/`，包含完整的harness快照
- 用户可以用`tail -f logs/current.jsonl`实时监控

**验证方法：** 用户可以在实验运行中随时`cat`任意文件查看当前状态，不需要理解任何内部数据结构。

### 4.3 精心设计ACI

**落地方式：**
- `teacher.py`的`--level`参数只接受1、2、3，传入其他值直接报错退出（防呆）
- `solver.py`的`--output`参数强制要求`.py`后缀（防呆）
- `verify_solution.py`对无效Python代码返回明确的错误码（1=语法错误，2=Z3错误，3=超时）
- 所有脚本的`--help`输出包含完整的参数说明和示例

**验证方法：** 故意传入错误参数，检查脚本是否给出清晰的错误信息而非静默失败或崩溃。

### 4.4 写操作单线程

**落地方式：** 整个S-ARGUS是单进程顺序执行。教师生成任务时，学生不执行；学生解题时，教师不生成；经验写入时，没有其他写操作。`experiences/`目录采用“只增不改”策略——一旦写入，不修改、不删除。

**验证方法：** 在实验运行中检查`experiences/`目录的文件创建时间，确认没有重叠的写入时间戳。

### 4.5 成本在架构阶段算清楚

**落地方式：** 开发文档中已明确每轮的token消耗上限（输入30000+输出8000），并在`log_round.py`中实时累计。累计超过预算的80%时发出告警，超过100%时自动停止。

## 五、S-ARGUS能证明什么、不能证明什么

### 5.1 能证明的

**第一，形式锚定是否有效。** 对比“有Z3锚定”和“无Z3锚定（LLM自评）”两种条件下的Δ_t曲线。如果前者稳定在0.1以下、后者持续扩大，就直接证明了形式锚定的必要性。这是ARGUS架构最核心的主张。

**第二，难度自适应是否有效。** 对比“有难度自适应”和“固定难度”两种条件下，任务难度从Level 1扩展到Level 3的轮次。如果前者显著更快，就证明了HAP种群博弈的核心机制有效。

**第三，经验沉淀是否有效。** 对比“有经验注入”和“无经验注入”两种条件下，相同任务的重复求解效率。如果前者在相似任务上的成功率显著更高，就证明了经验原则化的价值。

**第四，外环元修改是否有效。** 对比“有元修改”和“无元修改”两种条件下，200轮后的最终正确率。如果前者显著更高，就证明了元层面自修改的价值。

### 5.2 不能证明的

**不能证明跨域迁移。** S-ARGUS只做Z3任务，不涉及跨域。跨域迁移需要至少两个不同领域的任务（如Z3+数学证明），超出了最小验证的范围。

**不能证明多Agent协同。** S-ARGUS是单线程顺序执行，不涉及多Agent并行。多Agent的协同效应（如果有的话）无法被验证。

**不能证明大规模种群的优势。** S-ARGUS的“种群”只有3个角色顺序执行，不是真正的种群。PopuLoRA式的种群规模效应无法被验证。

**不能证明安全治理。** S-ARGUS的宪法是固定的12条规则，不涉及宪法进化。可进化宪法的安全性无法被验证。

### 5.3 论文中的定位

S-ARGUS的实验结果应被定位为**“最小可行验证”**——它不证明ARGUS完整架构的所有主张，而是证明其**最核心的两个机制**（形式锚定、难度自适应）在最小规模下有效。论文应明确写出：

> “本文的贡献不在于证明ARGUS完整架构的优越性，而在于提供一个可复现的最小验证，证明形式锚定和难度自适应这两个核心机制在有限算力下即可产生可测量的效果。完整架构的其他机制（跨域迁移、多Agent协同、可进化宪法）留待未来工作验证。”

这种诚实的定位反而会增加论文的可信度。审稿人更信任“我们证明了X，没有证明Y”的清晰边界，而非“我们证明了所有东西”的过度声称。


## 六、总结

S-ARGUS是一套符合五原则的简化架构：**6个工具、1个工作目录、3个角色、单线程执行、完整日志、成本实时监控**。它能验证ARGUS最核心的两个机制——形式锚定和难度自适应，总成本约150元，开发周期约5天。它不能验证跨域迁移、多Agent协同和安全治理，但这些可以在论文中作为“理论贡献”和“未来工作”呈现。

**关键判断：对于一篇独立研究者的论文，S-ARGUS的“窄而深”比ARGUS完整架构的“宽而浅”更有发表价值。** 一个真正跑过的、有完整日志的、可复现的最小实验，比一个华丽的、未经验证的完整架构，更能对抗“AI代写”的质疑。
