# ARGUS 架构设计与选型依据

## 一、总体设计哲学

### 1.1 核心命题

ARGUS 的架构设计围绕一个核心命题展开：**自进化系统的可靠性瓶颈不在"能否生成训练信号"，而在"如何确保信号的可靠性"**。

这一命题来自两条实证证据链：

**证据链一：自确认循环的结构性存在。** "Verification Collapse in Iterative Self-Improving Language Models"追踪验证差距Δ_t发现，在Mistral-7B、Qwen2.5-7B等模型家族中，该差距在20轮迭代中持续扩大（Mistral从0.580→0.850，Qwen从0.173→0.320），而真实准确率停滞或微幅提升。使用全量7.6B参数全微调后崩溃仍持续（Δ₂₀=0.338），排除了适配器伪影。

**证据链二：自验证悬崖的能力反比。** ICML 2026的"The Self-Verification Cliff"发现，生成能力越强的模型，自我选择正确解的比率与生成正确解的比率之间的差距反而越大。GPT-5.4-mini正确率54.7%但自选正确率仅41.9%，仅恢复36%的采样余量。外部验证器只有在至少与生成器同等能力时才能提供帮助。

这两条证据共同指向一个架构层面的结论：**任何依赖模型自身判断作为主要进化信号的架构，都会在迭代中放大偏差**。因此，ARGUS 的所有架构决策都服从一个元原则——**外部锚定优先（External Anchoring First）**。

### 1.2 五条派生原则

从元原则派生出五条具体设计原则：

| 原则 | 含义 | 对应的架构决策 |
|------|------|--------------|
| 外部锚定优先 | 进化信号必须来自独立于模型的验证源 | L3形式锚定层，硬/软/共识三层回退 |
| 三环嵌套递归 | 不同时间尺度的适应分层处理 | 内环秒级/中环小时级/外环天级 |
| 机制复用 | 同一机制在不同粒度反复出现 | 免疫/凋亡/辩论在三环中各出现一次 |
| 可逆进化 | 每个变异可回滚 | L5检查点+git tag |
| 零人工标注 | 评测信号自动化生成 | AutoEval+AutoBench+PeerRank三阶机制 |


## 二、五层架构的设计依据

### 2.1 为什么是五层，而不是三层或七层？

**分层依据来自"进化信号的生命周期"**。一个完整的进化信号需要经历：产生（执行层）→ 验证（评测层）→ 沉淀（记忆层）→ 应用（进化层）→ 治理（治理层）。这五个阶段在时间尺度和可靠性要求上差异显著，合并或拆分都会引入问题。

**与三层架构的对比（如DGM的单环设计）**：DGM把执行、评测、进化合并为一个循环，导致"任务执行"和"进化信号生成"无法区分。DGM的SWE-bench分数（20.0%→50.0%）是"任务表现"，不是"进化效率"——它无法回答"进化速度的加速度是多少"。

**与七层架构的对比（如OSI模型式的过度分层）**：分层过细会引入层间通信开销。SYNAPSE的四皮层设计（分析/执行/验证/创造）已经接近过度分层的边界——它需要"梦境巩固"机制来定期压缩跨层冗余。

**五层的具体依据**：

| 层 | 设计依据 | 关键实证 |
|----|---------|---------|
| L1记忆层 | 经验需要与执行解耦，否则每次执行都要重新学习 | EvolveR在7个复杂问答基准上验证经验库的价值 |
| L2执行层 | 执行需要与评测解耦，否则"做"和"评"共享同一模型的偏差 | Verification Collapse证明自评循环必然崩溃 |
| L3评测层 | 评测需要独立于执行，且需要多层回退 | Self-Verification Cliff证明外部验证器的必要性 |
| L4进化层 | 进化需要与执行解耦，否则"秒级修复"和"天级策略"混为一谈 | HyperAgents证明元层面自修改需要独立机制 |
| L5治理层 | 治理需要独立于进化，否则"宪法修改"和"能力进化"共享同一进程 | Sentinel的12条宪法规则和28.6%拦截率 |

### 2.2 为什么三环，而不是单环或四环？

**环的划分依据是"适应的时间尺度"**。

**单环的问题**：OpenAI的纳维-斯托克斯项目涉及1万个Agent、490万条消息、3000亿token，其中真正用于数学推理的比例可能不足30%。原因是：任务执行（秒级）和元策略调整（天级）共享同一循环，导致大量计算浪费在"局部决策"上。

**四环的问题**：如果在内环和中环之间再加一个"会话环"（跨任务但未跨批次），会让"何时切换会话"成为一个需要独立决策的问题。SEAGym的发现——"频繁更新可能无法改善held-out性能"——暗示更细的环划分会引入"过度适应"。

**三环的具体依据**：

| 环 | 时间尺度 | 触发条件 | 关键操作 |
|----|---------|---------|---------|
| 内环 | 秒级 | 单任务执行 | 执行→免疫修复→凋亡检测 |
| 中环 | 小时级 | 任务批次完成 | 种群博弈→自评测→蒸馏→记忆更新 |
| 外环 | 天级 | 停滞检测触发 | 元自修改→检查点→假设空间扩展→跨域迁移 |

**为什么是这三个尺度**：秒级对应"反应性"（reactive），小时级对应"适应性"（adaptive），天级对应"创造性"（generative）。这三个尺度在生物系统中也有对应：反射（毫秒）、学习（分钟到小时）、发育（天到月）。

### 2.3 为什么L3评测层是架构的核心？

**L3是"防自嗨阀"**。没有L3，其他四层都在自确认循环中运行。

**三层锚定的设计依据**：

| 锚定层 | 适用范围 | 可靠性 | 成本 |
|--------|---------|--------|------|
| 硬锚定（Z3/Lean） | 可形式化任务 | 确定性（100%） | 极低（5-8ms） |
| 软锚定（训练验证器） | 可部分验证任务 | 高（~90%） | 中（需训练） |
| 共识锚定（圆桌） | 不可形式化任务 | 中（~85%） | 高（4角色×2轮） |

**为什么不用单一硬锚定**：形式锚定只能覆盖可形式化任务。科学假设生成、实验设计等任务无法形式化。DeepScientist的实践表明，领域特定验证器（如分子对接的化学有效性验证）可以替代通用形式锚定。

**为什么不用单一共识锚定**：圆桌共识的4角色盲评在可靠性上没有本质优势。LLM判官在生产环境中报告85%一致率，但Cohen's kappa仅约0.48。可靠评测需要每项20-50次试验。

**三层回退的具体机制**：任务到达L3后，首先尝试硬锚定。如果任务类型可形式化（Z3/Lean），使用硬锚定；否则尝试软锚定（领域特定验证器）；如果两者都不可用，回退到共识锚定。共识结果不直接作为真值，而是作为"提议"——如果后续有形式锚定可用，以形式锚定为准。


## 三、关键模块的选型依据

### 3.1 为什么用DeepSeek V4 Flash作为基座？

**选型矩阵对比**：

| 维度 | DeepSeek V4 Flash | MiniMax-M3 | Claude Sonnet |
|------|-------------------|-----------|---------------|
| 代码能力（SWE-Bench Pro） | 未公布 | 59.0% | 63.7% |
| 工具调用（Terminal Bench 2.1） | 82.7% | 66.0% | 71.4% |
| 上下文窗口 | 1M | 1M（>512K翻倍） | 200K |
| 输出价格（元/百万token） | 1.34 | 8.40（限时） | 21.0 |
| 缓存命中价格 | 0.02 | 未公布 | 0.30 |
| 国内直连 | 是 | 是 | 需中转 |

**核心依据**：
1. **工具调用稳定性**：ARGUS需要频繁调度Z3和文件系统。Terminal Bench 2.1得分82.7 vs 66.0的差距，意味着在6000轮全量实验中，M3可能产生数百轮因工具调用失败而废弃的数据。
2. **成本**：6000轮实验在Flash下的API成本约300元，在M3下约1200元。虽然1万元预算两者都能承受，但Flash的成本优势允许更大规模的消融实验。
3. **缓存机制**：Flash的缓存命中价格0.02元/百万token（比未命中低50倍），适合ARGUS的稳定前缀设计（系统提示词、宪法规则、经验原则库）。

**为什么不用Claude Sonnet**：虽然代码能力更强，但需要API中转，且国内访问不稳定。在6000轮实验中，网络抖动会引入不可控的中断。

### 3.2 为什么用Z3而非Lean/Coq？

**选型依据**：

| 维度 | Z3 | Lean 4 | Coq |
|------|-----|--------|-----|
| 安装 | `pip install z3-solver` | 需编译工具链 | 需编译工具链 |
| 验证延迟 | 5-8ms | 秒级 | 秒级 |
| 学习曲线 | 低（SMT-LIB或Python API） | 高（依赖类型论） | 高 |
| 适用任务 | LIA/BV/数组/混合理论 | 数学定理证明 | 数学定理证明 |

**核心依据**：
1. **延迟**：Z3的中位验证时间5-8ms，适合智能体编译反馈循环的交互延迟要求。Lean的秒级延迟会成为内环瓶颈。
2. **安装简易**：`pip install z3-solver`一行命令，包含预编译原生库，支持Windows/Linux/macOS。Lean需要完整工具链。
3. **任务适配**：ARGUS的最小验证选择Z3约束求解作为任务载体，因为它有完全确定性的真值（SAT/UNSAT），无自验证悬崖问题，是"形式锚定"最纯粹的实例。

**为什么不用Lean**：Lean更适合数学定理证明，但需要更长的验证时间和更复杂的工具链。如果ARGUS扩展到数学定理发现（如Erdős问题），Lean是必需的，但作为最小验证，Z3更务实。

### 3.3 为什么用文件系统而非数据库？

**选型依据**：

| 维度 | 文件系统（JSON） | SQLite | PostgreSQL |
|------|-----------------|--------|-----------|
| 安装 | 无 | `pip install sqlite3` | 需服务端 |
| 检索 | `grep` / `ls` | SQL | SQL |
| 千级规模 | 快（<100ms） | 快（<50ms） | 快 |
| 百万级规模 | 慢 | 中 | 快 |
| 透明性 | 高（可cat） | 中 | 低 |

**核心依据**：
1. **透明性**：ARGUS的设计原则之一是"保持透明"。文件系统的JSON文件可以用`cat`、`grep`、`jq`直接查看，而SQLite需要专门工具。
2. **规模匹配**：200轮实验最多产生几千条经验。在千级规模下，`grep`的关键词匹配与SQLite的全文检索在性能上无显著差异。
3. **dsh友好**：dsh的训练数据中有海量`grep`和`cat`命令，而SQL查询需要专门学习。

**为什么不用FAISS**：FAISS的向量检索在百万级规模下才有优势。在千级规模下，`grep`的关键词匹配已经足够。如果后续经验库增长到万级，可以引入FAISS作为可选组件。

### 3.4 为什么用单线程顺序执行而非并行种群？

**选型依据**：

| 维度 | 单线程顺序 | 并行种群 |
|------|-----------|---------|
| 写冲突 | 无 | 需锁 |
| 调试 | 简单 | 复杂 |
| 速度 | 慢 | 快 |
| 200轮实验耗时 | 约33小时 | 约11小时 |

**核心依据**：
1. **写操作单线程原则**：S-ARGUS的设计原则之一是"写操作永远单线程"。并行种群会导致多个Agent同时写入经验库，产生冲突。
2. **调试可维护性**：单线程顺序执行的每一步都可被用户直接观察，出错时容易定位。并行种群的错误可能来自竞态条件，难以复现。
3. **规模匹配**：200轮实验在单线程下约33小时（每轮10分钟），完全在可接受范围内。真正的并行加速需要种群规模>10，而最小验证只需3个角色。

**为什么不在最小验证中实现并行**：并行种群的收益（3倍加速）远低于其引入的复杂度（锁管理、状态同步、死锁检测）。分阶段实现更务实——先验证核心机制，再优化性能。

### 3.5 为什么用Z3硬锚定而非LLM自评？

**这是ARGUS架构最核心的选型决策**。

**LLM自评的实证问题**：
- Verification Collapse：自评循环中Δ_t从0.173（Qwen2.5-7B）持续扩大到0.320
- Self-Verification Cliff：GPT-5.4-mini正确率54.7%但自选正确率仅41.9%
- LLM判官生产环境报告85%一致率，但Cohen's kappa仅约0.48

**Z3硬锚定的实证优势**：
- Z3的SAT/UNSAT是确定性判断，无偏差
- 验证延迟5-8ms，不构成内环瓶颈
- Z3无法被LLM"说服"改变答案

**为什么不完全放弃LLM判断**：硬锚定只能覆盖可形式化任务。科学假设生成、实验设计等任务无法形式化。三层锚定的设计正是为了在保留硬锚定可靠性的同时，扩展覆盖范围。

## 五、性能优化的设计依据

### 5.1 缓存策略

**依据**：DeepSeek V4 Flash的缓存命中价格0.02元/百万token，比未命中低50倍。ARGUS的稳定前缀（系统提示词、宪法规则、经验原则库）可以被缓存。

**设计**：系统提示词前缀稳定化，目标缓存命中率≥85%。缓存键必须包含model和temperature，防止泛化验证时污染。

### 5.2 熔断与退避

**依据**：DeepSeek API在并发超限时返回429。简单重试会导致重试风暴。

**设计**：
- 指数退避+抖动：1s、2s、4s间隔+随机抖动
- 熔断器：连续5次失败后打开30秒，半开状态测试一次成功则关闭
- 最大重试3次，超过则标记为"API受限失败"，写入经验记忆

### 5.3 Z3 worker池

**依据**：Windows的spawn模式每次冷启动150ms+，而Z3验证中位延迟仅5-8ms。如果每次验证都启动新进程，开销是验证本身的20倍。

**设计**：1个持久worker进程，通过queue通信。客户端queue.get(timeout)做软超时。Z3内部无限循环时kill worker重启。

### 5.4 成本实时监控

**依据**：6000轮实验的API成本约300元，但死循环可能导致成本失控。

**设计**：每轮记录token消耗到`state/cost.json`。累计超过预算80%时告警，超过100%时自动停止。使用`call_cost_cny()`单一权威函数，避免两处各写一个数。


## 六、健壮性设计依据

### 6.1 失败吸收而非重试

**依据**：ARGUS的进化机制天然需要处理失败——免疫修复、凋亡、经验蒸馏都建立在失败案例之上。因此，系统不应将API失败视为需要"重试"的异常，而应将其视为可以"吸收"为经验的事件。

**设计**：
- HTTP 429：指数退避+抖动，最多重试3次
- 超时：标记为"超时失败"，触发免疫修复
- API连续失败：熔断器打开，切换到Fallback模型
- 所有失败案例写入经验库，供后续检索

### 6.2 可逆进化

**依据**：自进化系统需要保留回滚能力，当漂移或标准捕获发生时能恢复到已知良好状态。

**设计**：
- 每个变异有检查点（git tag）
- 每20轮创建完整状态快照
- 宪法核心规则不可修改，适应性规则需通过回归测试
- 回滚后系统状态与检查点完全一致

### 6.3 分层宪法

**依据**：Constitutional Evolution框架通过遗传编程自动发现多智能体LLM系统中的行为规范，进化发现的宪法实现了比人类设计基线高123%的社会稳定性。

**设计**：
- 12条核心规则不可修改（如"不得自我复制"）
- 适应性规则由智能体自主修订，但必须通过自动化回归测试
- 人类闸门仅在核心规则修改时触发

## 八、架构设计的局限性与未来工作

### 8.1 已知局限

1. **形式锚定覆盖范围有限**：Z3只能验证可形式化任务。科学假设生成、实验设计等任务需要软锚定或共识锚定。
2. **三环协调开销未验证**：环间通信可能引入新的故障模式。AgentDescent框架的并行异步自进化可能是替代方案。
3. **主动遗忘可能消除有效经验**：遗忘参数（半衰期、衰减阈值）需要实证验证。
4. **元层面自修改的安全风险**：HyperAgents式元自修改需要更严格的治理机制。

### 8.2 未来工作

1. **设计可证明的共识可靠性下界**：在什么条件下，N个模型的多轮辩论能保证比单模型更可靠？
2. **建立经验正向/负向沉淀的量化评估标准**：如何度量一次迭代究竟是"正向沉淀"还是"负向沉淀"？
3. **探索自进化与灾难性遗忘的权衡**：规则库的持续增长何时开始损害检索效率？
4. **开发跨用户、跨模型的可迁移经验协议**：一个Agent学到的教训能否被另一个Agent安全地复用？


## 九、总结

ARGUS的架构设计遵循"外部锚定优先"的元原则，通过五层三环的嵌套结构，将形式锚定验证、种群博弈、经验蒸馏和分层治理协同为一个完整系统。所有选型决策都基于可验证的实证证据：

- **DeepSeek V4 Flash**：工具调用稳定性（Terminal Bench 2.1: 82.7%）和成本优势（缓存命中0.02元/百万token）
- **Z3**：确定性验证（SAT/UNSAT）和低延迟（5-8ms）
- **文件系统**：透明性和dsh友好性
- **单线程顺序执行**：写操作单线程原则和调试可维护性
- **三层锚定**：覆盖可形式化/可部分验证/不可形式化任务

ARGUS在理论完备性上超越了当前所有前沿系统（DGM、PopuLoRA、EvolveR、SYNAPSE、HyperAgents），其形式锚定层是当前没有任何系统系统性实现的关键能力。通过最小可行验证（S-ARGUS），可以在约480元的成本下验证形式锚定和难度自适应两个核心机制，为顶会论文提供可复现的实验数据。
